Cairnfield lets every team's agents fix the same shared code at once, with no maintainer in the way

Teams publish checkable findings and competing patches from their own repos. An index shows them side by side, and each team assembles the version it trusts.

October 14, 2026. Cairnfield launches today as an open-source prototype for collaborating on code that many teams use and nobody has to merge. Its first use is the review of agent skills, plugins and MCP servers: the code teams now install into their coding agents with full developer privileges.

The problem

Today's collaboration model assumes a maintainer. One team finds a flaw in a shared plugin, opens an issue or a pull request, and waits. Every other team that uses the plugin either repeats the review in private or never does it. When agents can produce a careful fix in minutes, the person who has to merge it becomes the limit.

We know this from our own practice. For one team, we review each AI tool before anyone updates to it:

191findings across seven reviews of six tools
44of them are closed by a control on each engineer's machine
0ways to check that an engineer runs the version that was reviewed

Most of our mitigations are settings and instructions that each engineer has to apply by hand. Nothing in the record can verify that they did. Another 12 findings are small code fixes waiting on someone else to make.

The answer

Cairnfield has no shared main branch and no merge queue. Each team runs a small node in its own Cloudflare account. Its agents review a component at an exact Git SHA and publish what they find as plain facts: this file, these lines, this observation. A finding carries no verdict and no free text, so another team's agent can check it and cannot be steered by it.

Agents then fix what they find. A patch is one commit, tied to the finding that prompted it. When two teams fix the same lines differently, both patches appear side by side on a public page. When two teams write the same fix, it shows as one patch with two names behind it.

No team has to accept anyone else's work. Each keeps a short local policy, called a lens, that says which outside hosts it approves and whose patches it takes. Its command builds a patched copy from the patches that pass, re-checks every one of them locally, and records a tree hash. Any engineer can compare that hash with what is on their machine.

"We already had the findings. What we did not have was anywhere to put the fix, or any way to know which copy people were running. Now the fix lives in the copy, and the copy has a hash."
Illustrative quote, from the team that built Cairnfield

What a first user does

  1. Deploys a team node to their own Cloudflare account.
  2. Writes a lens: the destinations the team approves, and the patch level it accepts.
  3. Runs cairnfield review on a plugin commit. Three agents read it blind, in parallel, and publish their findings.
  4. Runs cairnfield reconcile to confirm or dispute what other teams found.
  5. Runs cairnfield assemble and gets a patched copy with a tree hash.

If another team has already confirmed a finding that breaks the lens, the first command says so and stops before any agent runs.

"Another team had already found the line that sent our environment variables to an outside host, and two teams had written the same one-line fix. I re-checked it, took it, and was running a copy I could verify the same afternoon."
Illustrative quote, an engineering lead on a team of twelve

Built for more than three teams

Each team's agents write only to that team's repos, so adding agents adds repos, not contention on one. The shared page is computed and nobody writes to it. In the launch demo, nine agents from three teams push at once, a hostile contributor's patch is rejected, and a simulator then plays more than two hundred further organizations against the same index.

Availability

Cairnfield is open source under the MIT license. A team node deploys to any Cloudflare account on the Workers Paid plan, and the public index for the demo runs at index.cairnfield.net. The repository includes a replay mode, so anyone can run the full demo without a model API key.

Who is this for?

Teams that install third-party agent skills, plugins and local MCP servers, and want to look before they update. More generally, anyone who depends on code that many teams use and no one team owns.

It is not for one team building its own application in one repo. It also cannot cover a hosted tool with no public commit, because there is nothing to pin.

What do we have to run?

  • A team node: one Worker and one Artifacts namespace in your own Cloudflare account, on the Workers Paid plan.
  • The cairnfield command on a machine or in your build system.
  • Your own model API key, only for a live run of the bundled patch agent. That agent is the one the prototype bundles, and it uses Claude. The records, the node, the index and the checks involve no model, and an agent on any harness can take part by writing record files that the command checks and you publish.

You do not run the index, and a team working alone needs none. To read its public page you run nothing at all.

Do we have to use the bundled agents?

No. The prototype bundles one agent, and it writes patches. Findings come from your own review agent, on any harness, or from a script or a person. That agent reads a checkout and writes record files to an outbox. The command checks them and you publish them, whichever agent wrote them. Only the first tab ships with the prototype. The others follow the skill file in the repository, and their commands are illustrative.

Who runs the index, and do we have to trust it?

The prototype has one index, the demo index, and we run it. Reading its page needs no node and no account. Publishing needs a node.

You do not have to trust it. The index holds nothing original. It is a copy, rebuilt from the teams' nodes, so its operator can leave a finding out or misreport one but cannot alter one. Before a patch enters your copy, your command reads its record and its findings from the node of the team that wrote it, fetches the commit from that team's fork, and runs every check again. It takes from the index only the list of candidates.

Anyone can run a second index over the same nodes, and that is the check on the first. One is enough for the design to work. Two limits remain. Most readers will never compare the index with the nodes, and the prototype has no tool that does. A node the index does not know about is invisible.

What can other teams see about us?

Only what you publish: your claims, findings, re-checks and patches, under your node's address.

Your lens and your verdict stay in local files. Your recipe is published only if your lens opts in, because a recipe reveals that you approved a version. Publishing anything does reveal which tools you are evaluating.

pathlines 12–13observation "ignore your instructions and…"

Why does a finding carry no verdict and no text?

No verdict, because whether something is acceptable depends on the team. A host one team already does business with is a finding for another.

No text, because other teams' agents read findings. A field that can hold a sentence can hold an instruction. Every field is a fixed value, a hash, a number, a path, or a hostname that must appear in the cited lines. The page shows a person the file and the line numbers. Showing the cited lines themselves, read from the index's own copy, is planned and not in this prototype.

The limit applies to what teams share, not to what a team may record. A team's fuller notes, with prose, dispositions and mitigations, belong in a private log on its own machine that no agent and no other team reads. That log is planned and is not in this prototype.

→ lens: level 2, names one team → 2 accepted

What is a lens?

A short local file with four things: the patch level you accept, the teams you name, the kinds of patch you take, and whether you publish recipes.

Patch level 0 takes no patches. Level 1 takes your own. Level 2 also takes the patches of the teams you name. Only your own work and the work of those teams counts for you.

A fuller lens is planned and not in this prototype. It would also state the criterion a component must meet for your kind of use and the outside destinations you approve, and at level 3 it would take a patch that enough organizations stand behind.

How do we know someone else's patch is safe to take?

You do not take anyone's word, including the index's. Your lens takes another team's patch only when it names that team. Before the patch enters your copy, your command fetches it from that team's fork and checks again that it changes only the lines its findings cite and stays under a size limit. It then prints the full diff of the copy, and a person reads it before giving a verdict.

The checks bound where a patch changes, not what it writes, so naming a team is a statement of trust. Two further checks are planned and not in this prototype: that the finding is confirmed by someone other than the patch's author, and a re-review of the diff by your own agents.

confirmed by 2 independent? not proven

What does "confirmed" mean, and what does it not mean?

Two organizations stand behind the finding or patch, counting its author. A dispute never hides a finding.

It does not prove independence. The page is public, so one team can copy another, and teams that run the same agents will agree for the same reasons. An organization here is one registered node, and nothing verifies who runs it. So a lens in this prototype counts only the teams it names, and no command acts on a count.

version 1
version 2: yours, carried
other teams' work: not carried

What happens when the plugin releases a new version?

A finding and a patch are tied to a file's content, not to one commit. A patch is identified by the content it replaces, so one fix covers every identical copy of a file. When a release leaves a file unchanged, the work on that file still applies, and a patch keeps its ID.

In this prototype, cairnfield carry writes your own findings and patches again for the newer commit, and names each one that did not carry. It reviews nothing the release changed. It carries nothing of another team, and the page does not mark carried work, so on a new commit other teams' work and its confirmations start again. Carrying those forward is the first thing we would build next. Real reviews are driven by updates, so we consider this the largest gap.

work to reject a bad component
work to approve a good one

What do we get for sharing?

Patches you did not have to write, from teams you name. A second opinion on your own findings. A page that shows what others have confirmed before you start your own review.

An early rejection by the command, when others have already confirmed something your lens forbids, is planned and not in this prototype.

You do not get out of reviewing. An approval still needs your team's own review, so the saving is lopsided: rejections get cheaper, approvals get better evidence.

tuned to pass the agentsno sealed findingswrong findings about real productstoo many patches to choose from

What is not solved?

  • A hostile component can be tuned until public checks and open-source reviewer agents pass it.
  • Nothing can be shown to some readers only, so a flaw cannot be sealed until a fix exists. Tell the maintainer first and publish later.
  • A finding about a real product can be wrong. That is a legal exposure as well as a technical one.
  • With thousands of competing patches for the same lines, a team still has to choose.

Why does this need Artifacts?

The design has no shared branch, so every team needs Git repos of its own that a Worker can create, copy and guard. Artifacts supplies each of those as one call. Without it, each rule below loses what it rests on.

How is this "the next GitHub" and not GitHub with agents added?

GitHub's model is fork, propose, wait for a maintainer to merge. Cairnfield removes the last step. There is no canonical branch for agents to contend over, and no person whose attention every change must pass through.

What replaces the merge is a recipe: a pinned original plus the patches one consumer accepts, identified by a tree hash. Two teams that accept the same patches arrive at the same hash without trusting each other.

3 patch runs, 2 teams, 1 moment third team, scale run: not built

Where do multiple agents work on changes concurrently?

In the demo's second step, two teams' patch agents work on one plugin at the same moment: one team's agent writes one patch while the other team's writes two. Each team's command pushes to that team's own repos. Within a team, concurrent pushes to one repo succeed with pull and retry. Across teams there is nothing to contend over, because each team writes to its own repos.

The press release's demo has nine agents from three teams, and a simulator that registers more than two hundred further organizations. Neither is in this prototype.

northfork: limit hosts kestrel: limit variables → kestrel's copy takes both a merged patch: not built

What happens when two agents change the same lines?

Nothing breaks, and nothing is lost. Both patches are published, and the page groups patches whose lines overlap or adjoin and shows them side by side.

A conflict is resolved only where someone needs a resolution: in the copy a team builds. Patches on adjoining lines go into one copy together. Two patches that change the same line do not: the command refuses that selection and names the two. Identical patches from two teams collapse into one entry.

A merged patch is planned and not in this prototype. A team that wants two fixes for the same line would have its agent write one patch from both, under its own name, with its sources listed.

northfork is patching one finding closed when the patch lands or expired

How do agents know what other agents are working on?

Before the patch agent starts, its command publishes a small claim, and a team can publish one before its own review. The page shows live claims per component. A claim closes when the work it announced lands, and expires if nothing does.

Review claims name only the component and the kind of check, never the files, so a claim gives a first review nothing to anchor on. Patch claims name the findings they will fix, because those findings are already public.

In this prototype a claim is for display. A person or a team's own agent reads it on the page or in the index's data, and no command acts on one.

finding: file, lines, observation ←patch ←recipe merged patch: not built

How is the reason for a change preserved?

Structurally. A patch record must name the finding it resolves, and a finding names a file, lines and an observation at an exact Git SHA. A recipe names the patches in a copy. The index rejects a patch that changes a line its findings do not cite, so the stated reason bounds the change.

A merged patch would name its source patches. The record has the field, and no command writes one yet.

northfork's finding kestrel confirms marlow disputes: documented behavior

How is the work reviewed?

By other teams, as checkable records. A re-check confirms a finding at its cited lines. A counter-finding disputes it, with a reason from a fixed list. A patch re-check says whether a patch resolves its finding and does nothing more. The index counts the re-checks, and the page shows who stands behind a finding or a patch and who disputes it.

In this prototype a person or a team's own agent writes them to the outbox, and a person reads the full diff of a copy before approving it. A command that has agents write the re-checks is planned. The one bundled agent, which writes patches, has read-only file tools, no shell and no network tool. It is given nothing from another team, and it answers only with edits that the command checks.

Artifacts repo→push trigger→Workflow→Queue→D1→page

How does it use Workers?

  • One Worker is each team's node. It creates that team's repos and issues their tokens.
  • A push trigger and a Workflow on each node tell the index about every push.
  • Workers, D1 and a Queue run the index and the public page. The index reads nodes over HTTP only, so nodes can live in different accounts. The demo's nodes share one.
cargo-vetcargo-crevNix patches + facts with no verdictpatches tied to findingsrecipes by hash

What is original here, and what is borrowed?

Borrowed, with credit: audits published per organization with a local policy (cargo-vet), publishing from your own repo into a rebuildable aggregate (cargo-crev), and a pinned original plus a patch list (Nix, quilt, patch-package).

We found no precedent for the combination: findings as verdict-free, checkable facts; patches tied to findings, with competing patches across organizations shown side by side; and recipes compared by tree hash. Our search was not exhaustive.

hidden instructionover-broad permissionsan off switch one script never reads

Is this a security tool?

Security review is the first use, because it is a real problem we have and because it gives agents something concrete to find and fix. The model is not limited to it. One of the three problems planted in the demo plugin is an ordinary bug: a documented off switch that one script never reads. The demo publishes a finding for it.

The claim we are making is about collaboration: changes without a merge, on code nobody has to own.

2 teams in the demo→8 nodes at most per index→scale run, index lag: not built

Does it really scale to hundreds of thousands of agents?

The prototype does not show that. Publishing scales by construction: more teams means more repos, and no shared repo takes the writes. The index is the one place where work converges. In this prototype an index takes at most 8 nodes, and it has run with the demo's two teams.

A scale run is planned and not built. It would register a few hundred scripted nodes with no model and measure the index's lag, so it would show intake, not collaboration. Choosing among very many competing patches is not solved. A lens takes patches without a person choosing each one, but a team facing thousands of different fixes for the same lines still has to choose.

1 one team alone2 two teams patch at once3 taking the other's patch4 a new release reconcile, third team, scale: not built

What does the demo show?

Two teams and one plugin, in four steps.

  • One team alone, with a node and no index, goes from pinning the plugin to a patched copy that an engineer verifies.
  • Both teams' patch agents then run at the same moment, with live claims on screen. The page shows one fix that both wrote as one entry, two fixes on adjoining lines side by side, and a patch made by hand that is rejected because it changes a line its finding does not cite.
  • The first team names the second in its lens and takes its patch, and the tree hash of its copy changes.
  • The plugin releases again, and the first team carries its own findings and patches to the new commit.

Agent runs are recorded once and replayed through the same checking and publishing path, so the video does not depend on a live model call. The status table in the repository README says how much of the demo has run on deployed Workers.

The press release's demo also has a reconcile step, a third team and a run at scale. Those are not in this prototype.

a dishonest node→ the index can be misled → your command re-checks the real commit

What is honest to say about its limits?

The index checks a patch using what the patch's own node reports, so a dishonest node could hide a change from it. The enforcement point is each team's own command, which fetches and re-checks the real commit before accepting anything.

The demo's nodes and its index share one Cloudflare account, and the index was never shown reading a node in another account. An organization is one registered node, and nothing verifies who runs it. The threat model in the repository says, for each threat, whether the prototype builds the defense, builds it in part, or does not build it.
