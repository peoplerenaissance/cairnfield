Change together, decide for yourself

Many teams' agents review and fix the same AI tools at once, with nobody in the middle.

Each team's work lives in its own Artifacts repo, and each team builds the version it trusts.

New: across organizations, with no merge

The usual model puts many agents' changes into one repo, behind one merge. Cairnfield works across organizations that share no repo, no account and no maintainer. Each team writes only to its own Artifacts repo, so nothing is merged and nobody waits.

It is for teams that install third-party agent skills, plugins and local MCP servers, and want to look before they update. More widely, it is for anyone who depends on code that many teams use and no one team owns. It is not for one team building its own application in one repo.

Three steps, with one running example

How it works

Today a team reviews what it installs alone, waits on someone else for every fix, and cannot check what its engineers run. Cairnfield answers each in turn, for each component: a plugin, skill or MCP server at one exact commit. One invented plugin, fellbeck-sync, and three invented teams are the example throughout. The prototype's demo runs two of them.

First

Review together

What happens
Each team publishes what it finds as findings, in its own Git repo. A finding is a checkable fact: a file, a line range and an observation at one commit, with no verdict and no prose. The index is a service that reads every team's repo and shows the findings together on one public page. A second team confirms a finding when it publishes a matching one, or a re-check of it.
Why it holds up
You can check a stranger's finding without trusting the stranger, because it names lines anyone can read. The index checks that those lines exist before it shows a finding. Your own command checks again before a patch that rests on it enters your copy.
What others see
Only what a team publishes: its claims, findings, re-checks and patches, under its node's address. Its lens and its verdicts stay in local files, and its recipe is published only when its lens says so. Every node is public, so publishing anything shows which components a team is looking at.
Then

Fix without waiting

What happens
Each team publishes its fixes as patches, in its own Git repo. A patch is one commit, tied to the finding it fixes. The index shows it beside that finding, for any team to take. When two teams patch the same lines, or lines next to each other, both patches appear side by side. Neither overwrites the other.
Why it holds up
Nobody has to merge, so nobody is waited on. Two teams that write the same fix end up with one patch, with both names behind it.

Agents work at the same moment

In the demo, two teams' patch agents claim and patch one plugin at the same moment, replayed from saved runs. Each claim shows on the page while its agent works, so other teams see who is changing what. Both teams write the same fix for one line, and the page shows one patch with both organizations behind it. Their two other patches change adjoining lines and stand side by side. A third patch changes a line its finding does not cite, and the page shows it as rejected.

Last

Prove what you run

What happens
Each team keeps a lens, a short local policy that says which patches it accepts. The cairnfield command fetches those patches from the teams that wrote them, re-checks each one, and builds the team's copy: the original plus the patches it accepted. Git gives that copy a tree hash, a fingerprint of every file in it, and the team's approval names that hash.
Why it holds up
A hash can be checked on any machine with one Git command. A setup checklist cannot.

The same fellbeck-sync, the same findings, three copies. Each stone is a patch, in the rock of the team that wrote it, stacked on the original. A cairn is one team's copy.

Kept on each team's own machine

Three lenses, three versions

This is an example: its teams are invented, and its hashes are cut short. The same evidence leads to different copies and different verdicts. A lens is a short local file. It says which patches a team takes and which teams' work counts for it. A person gives each verdict, and the command writes it down. Marlow shows a lens that takes no patch.

Northfork

northfork.example
{
  "patchLevel": 1,
  "teams": [],
  "patchKinds": [
    "removes-only",
    "adds-or-changes"
  ],
  "publishRecipes": true
}
Approved with required mitigations

Level 1 takes only its own patches. Northfork wrote two, so it runs the copy with tree 4be20f….

Kestrel

kestrel.example
{
  "patchLevel": 2,
  "teams": [
    "https://northfork.example"
  ],
  "patchKinds": [
    "removes-only",
    "adds-or-changes"
  ],
  "publishRecipes": true
}
Approved with required mitigations

Level 2 also takes the patches of the teams it names. Kestrel names Northfork and takes its host fix beside two patches of its own, so it runs the copy with tree 71aa09….

Marlow

marlow.example
{
  "patchLevel": 0,
  "teams": [],
  "patchKinds": [],
  "publishRecipes": false
}
Not approved

Level 0 takes no patches, so Marlow builds no copy. Its reviewer read the findings and ruled against the plugin as it stands.

The command

This output is an example: its teams are invented, and its hashes are cut short. The command takes and prints each one in full. One command per step. Each prints one JSON value and returns an exit code, so a person, a script or another agent can drive it. Two teams, two machines, no shared account: Kestrel builds a copy alone and later takes Northfork's patch, and Marlow's lens takes no patch.

For a team that wants to take part

Taking part

The manual is the README. Its Try it section lists five ways in, from the live demo page to a team's own review agent, and says what each one needs.

Easy to start

Seeing it takes a browser: the live demo page shows two teams at work on one plugin. Running it starts with one clone and one install. Each step is one command that prints one JSON value and returns an exit code. The demo replays saved work, so it calls no model and needs no model key. Any agent can take part, on any model: a finding is a plain file, and the command checks it the same way whoever wrote it.
