Trust your whole AI toolchain?

Trust is earned, not assumed. Apply your own evaluation criteria to evidence about each exact version, collected by everyone who uses it.

Plugins, agent skills and MCP servers change with every release. With Cairnfield, your team's agents review them together with other teams', fix what they find without waiting on anyone, and prove which version you run.

Built on Git, on Cloudflare Workers and Artifacts. Each team's findings and patches are commits in its own repo, pinned to the exact Git SHA it reviewed. No shared branch, no merge, no maintainer: each team assembles its own version from work it can check.

For the engineer responsible for what the team installs

The problem, the answer, and why it fits

Three things go wrong when one team reviews the tools it installs. Each has one answer in Cairnfield, and one reason the answer holds up when the other teams are strangers.

The problem
The answer
Why it works
Every team reviews alone, or not at all. The same plugin is read in private by each team that uses it, and by nobody for the rest.
Teams publish what they find as checkable facts: this file, these lines, this observation. No verdict, no prose.
You can use a stranger's finding without trusting the stranger. Your own agent re-checks the lines before anything counts.
The fix waits on someone else. In our own reviews, a small code fix gets "tracked as follow-up": a note, and no place for the fix to go.
Each team publishes patches tied to findings, and builds its own copy from the patches it accepts.
Nobody has to merge, so nobody is waited on. Two teams that write the same fix end up with the same stone.
Nothing verifies what an engineer installed. In our own reviews, 44 of 191 findings are closed by a control on each person's machine: a setting, a written instruction or a tool left uninstalled. The record cannot tell whether it is there.
tree 71aa09…A patched copy has a tree hash, and your team's approvals name it.
A hash can be checked on any machine with one Git command. A setup checklist cannot.

What you need

  • A node in your own Cloudflare account, on the Workers Paid plan.
  • Your own model API key for the reviewer agents.
  • Publishing reveals which tools your team is evaluating.
  • An approval still needs your own review. Sharing makes rejections cheap and approvals better evidenced; it does not remove the work.

The loop, in order

How it works

Three things happen, in this order, for every component version. Everything a team publishes is a small file in its own Git repo.

First

Publish facts

A finding names a file, a line range and an observation at one commit. Each organization that stands behind it adds a stone. A dispute sits beside the stack and removes nothing.

both shown, side by side a third patch touched an uncited file: rejected
Then

Publish fixes

A patch is one commit tied to its finding. It is identified by the content it replaces, so one fix covers every identical copy of a file and keeps its identity when a release leaves that file unchanged. Competing patches for the same lines sit side by side. The index rejects a patch that touches content its finding does not cite.

kestrel's copytree 71aa09…3 patches, 2 teams
approved with required mitigations
Last

Build your own copy

Each team's lens picks the patches it accepts. Its command fetches them from the teams that wrote them, re-checks them, and builds a copy that anyone can verify by its tree hash.

Any agent can take part

The records, the node, the index and the checks involve no model. An agent on any harness reviews a checkout, writes record files to an outbox, and the command validates and publishes them. Only the first tab ships with the prototype; the others follow the skill file in the repository, and their commands are illustrative.

$ cairnfield review 9f3c1e7a
3 agents on the Claude API, read-only file tools, no network
outbox: 4 findings written
validated 4 · published 4 · head 5d10c3…

The bundled reviewers. The command runs them, so no agent ever holds the repo token.

$ codex exec "Follow skills/cairnfield/SKILL.md. Review .cairnfield/work/9f3c1e7a/checkout and write findings to .cairnfield/outbox."
… wrote outbox/finding/3f0a….json, outbox/finding/b81c….json
$ cairnfield publish 9f3c1e7a
validated 2 · published 2 · head 7c44e1…

Another vendor's agent reads the skill file and writes the same record files. Publishing is unchanged.

$ gemini -p "Follow skills/cairnfield/SKILL.md. Review .cairnfield/work/9f3c1e7a/checkout and write findings to .cairnfield/outbox."
… wrote 3 files to outbox/finding/
$ cairnfield publish 9f3c1e7a
{"record":"outbox/finding/91d2….json","reason":"unknown-value","field":"observation"}
validated 2 · rejected 1 · published 2

The checks do not care who wrote a record. A field outside the vocabulary is refused before it is published, whichever agent produced it.

$ ./scan-hosts.sh checkout/ > .cairnfield/outbox/finding/a0c7….json
$ cairnfield validate
1 record · ok
$ cairnfield publish 9f3c1e7a
validated 1 · published 1

No model at all. A script that finds outside hosts writes a finding against the published schema, and it counts the same as any other.

For a team that wants to take part

Run your own node

A team node is the one piece of Cairnfield you host: one Worker and one Artifacts namespace in your own Cloudflare account. It holds your team's records, your pinned copies of the components you review, and your patches. Two ways to deploy it give the same node.

What you need

  • A Cloudflare account on the Workers Paid plan, which Artifacts requires. Usage beyond the included amounts is billed to you.
  • An admin key that you choose. Your own command uses it to manage your node, and nobody else should have it.
  • The address of the index you want to notify. It defaults to the demo index.

What stays yours

  • It gives us no access to your account, your repos or your key.
  • It does not register your node with any index. You do that with the command.
  • It does not install the cairnfield command or run any review.
  • It publishes nothing. A new node is empty until you push to it.

Switched off for now. Cloudflare's one-click button does not yet list Artifacts, Workflows or push triggers among the services it sets up, and a node needs all three. We will turn it on when it does. Until then, the setup script deploys the same node.

you click→ a copy of the node's code in your Git account→ a Worker in your Cloudflare account→ your node, at your own address

What the button does

  • Opens Cloudflare's setup page, where you sign in, choose your account, and can rename the repository and the Worker.
  • Copies the node's code into a new repository in your own GitHub or GitLab account.
  • Builds and deploys the Worker, with a Workflow that runs on each push to your repos.
  • Sets up automatic builds, so a push to your copy redeploys your node, and gives each pull request a preview address.

What the setup page asks for

  • A GitHub or GitLab account for the copied code.
  • The admin key, with a note on the setup page saying how to generate one.
  • The index address, prefilled with the demo index.
$ git clone https://github.com/OWNER/cairnfield && cd cairnfield/node
$ nvm use && npm install
$ npx wrangler login
$ npx wrangler secret put ADMIN_KEY
paste the key you generated, for example with: openssl rand -hex 32
$ npm run deploy
Deployed cairnfield-node · https://cairnfield-node.YOUR-ACCOUNT.workers.dev
Artifacts namespace, Workflow and push trigger set up

The script runs Wrangler from the node's own directory, which is self-contained. It needs Node 22. Point your command at the address it prints, and run cairnfield pin to review your first component. The repository address above is a placeholder until the repository is public.
