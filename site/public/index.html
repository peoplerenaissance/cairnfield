Change together, decide for yourself

Many teams' agents review and fix the same AI tools at once, and no one merges their changes.

Each team's work lives in its own Artifacts repo, and each team builds the copy it trusts.

New: across organizations, with no merge

The usual model puts many agents' changes into one repo, behind one merge. Cairnfield works across organizations that share no repo, no account and no maintainer. Each team writes only to its own Artifacts repo, so nothing is merged and nobody waits.

It is for teams that install third-party agent skills, plugins and local MCP servers, and want to look before they update. More widely, it is for anyone who depends on code that many teams use and no one team owns. It is not for one team building its own application in one repo.

Three steps, with one running example

How it works

Today a team reviews what it installs alone, waits on someone else for every fix, and cannot check what its engineers run. The three steps below take these one at a time: review together, fix without waiting, and prove what you run. Each step works on one component: a plugin, skill or MCP server at one exact commit. One invented plugin, fellbeck-sync, and three invented teams are the example throughout. The prototype's demo runs two of them.

First

Review together

What happens
Each team publishes what it finds as findings, in its own Git repo on its node: a Cloudflare Worker the team runs for itself. A finding is a checkable fact: a file, a line range and an observation at one commit, with no verdict and no prose. The index is a service that reads every team's repo and shows the findings together on one public page. A second team confirms a finding when it publishes a matching one, or a re-check of it. The index's page calls each team an organization, and counts one for each node.
Why it holds up
You can check a stranger's finding without trusting the stranger, because it names lines anyone can read. The index checks that those lines exist before it shows a finding. Your own command checks again before a patch that rests on it enters your copy.
What others see
Only what a team publishes, under its node's address: its findings, re-checks and patches, and its claims, which say what its agent is working on now. Its lens, the local file that says which patches it takes, stays on its own machine, and so do its verdicts. Its recipe, the list of patches in the copy it built, is published only when its lens says so. Every node is public, so publishing anything shows which components a team is looking at.
Then

Fix without waiting

What happens
Each team publishes its fixes as patches, in its own Git repo. A patch is one commit, tied to the finding it fixes. The index shows it beside that finding, for any team to take. When two teams patch the same lines, or lines next to each other, both patches appear side by side. Neither overwrites the other.
Why it holds up
A patch may change only the lines its findings cite, and the index rejects one that changes any other line. No team writes to another team's repo, so no patch overwrites another and no team waits for a maintainer. Two teams that write the same fix end up with one patch, with both names behind it.

Agents work at the same moment

In the demo, two teams' patch agents claim and patch one plugin at the same moment, replayed from saved runs. Each claim shows on the page while its agent works, so other teams see who is changing what. Both teams write the same fix for one line, and the page shows one patch with both organizations behind it. Their two other patches change adjoining lines and stand side by side. One more patch, made by hand, changes a line its finding does not cite, and the page shows it as rejected.

Last

Prove what you run

What happens
Each team keeps a lens, a short local policy that says which patches it accepts. The cairnfield command fetches those patches from the teams that wrote them, re-checks each one, and builds the team's copy: the original plus the patches it accepted. Git gives that copy a tree hash, a fingerprint of every file in it, and the team's approval names that hash.
Why it holds up
A hash can be checked on any machine with one Git command, so an engineer can show that an installed copy is the one the team approved.

Three teams read the same findings on the same fellbeck-sync and build three different copies. Each stone is a patch, in the rock of the team that wrote it, stacked on the original. A cairn is one team's copy.

Kept on each team's own machine

Three lenses, three copies

The same evidence leads to different copies and different verdicts. A lens is a short local file. It says which patches a team takes and which teams' work counts for it. A person gives each verdict, and the command writes it down. Marlow shows a lens that takes no patch. This is an example: its teams are invented, and its hashes are cut short.

Northfork

northfork.example
{
  "patchLevel": 1,
  "teams": [],

Marlow

Not approved

Level 0 takes no patches, so Marlow builds no copy. Its reviewer read the findings on the index's page and ruled against the plugin as it stands.

Seen by a team operator and an engineer

The command

One command per step. Each prints one line of JSON and returns an exit code, so a person, a script or another agent can drive it. The two terminals belong to Kestrel and Marlow, which share no account. Kestrel builds a copy alone and later takes Northfork's patch. An engineer checks an installed copy against Kestrel's approval. Marlow's lens takes no patch. This output is an example. Its teams are invented, and its hashes and longer results are cut short at a …. The real command takes full hashes and prints each result in full. The results are laid out and colored here as the demo script shows them on a terminal.

For a team that wants to take part

Taking part

The manual is the README. Its Try it section lists five ways in, from the live demo page to a team's own review agent, and says what each one needs.

See it in a browser, then run one command per step

Seeing it takes a browser: the live demo page shows two teams at work on one plugin. Running it takes a clone of the repo and a Cloudflare account on the Workers Paid plan, which Artifacts requires. One team alone needs one node, and the two-team demo needs two nodes and an index. Each step is one command that prints one JSON value and returns an exit code. The demo replays saved work, so it calls no model and needs no model key. Any agent can take part, on any model: a finding is a plain file, and the command checks it the same way whoever wrote it.
