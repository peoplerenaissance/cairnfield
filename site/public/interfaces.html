Cairnfield

Change together, decide for yourself. Sketches of the six places a person meets the system. They were first drawn before the build, and they now follow what the prototype does.

A dotted outline marks a part of the first sketches that is not in this prototype. Everything here is mock data. The plugin, hosts and organizations are invented. Each stone stands for one organization or one patch. Each team has its own rock: Northfork is slate, Kestrel is sandstone and Marlow is ironstone. The prototype's demo runs two teams, and Kestrel and Northfork stand for them here.

The command

One command per step. Each prints one JSON value and returns an exit code, so a person, a script or another agent can drive it. Two teams, two machines, no shared account: Kestrel on the left, which builds a copy alone and later takes Northfork's patch, and Marlow on the right, whose lens takes no patch. One command for a whole review · not in this prototype

Two commands in the first sketch are not built

review would check the lens against confirmed findings and stop early, publish claims, run three reviewer agents that read nothing from other teams, then validate and publish. reconcile would have agents re-check other teams' findings and patches. The prototype bundles no reviewer agent. A team's own review agent writes its findings to the outbox, and a person or that agent writes a re-check or a counter-finding there.

cairnfield review 9f3c1e7a…
cairnfield reconcile 9f3c1e7a…

Kept on each team's own machine

Three lenses, three versions

The same evidence leads to different copies and different verdicts. A lens is a short local file. It says which patches a team takes and which teams' work counts for it. A person gives each verdict, and the command writes it down. The demo runs the first two teams. Marlow shows a lens that takes no patch.

A fuller lens · not in this prototype

Criteria, approved destinations and a level 3

The first sketch gave a lens three more things: the criterion each kind of use requires, the outside destinations a team approves, and a number of confirmations. A destination finding would then count against one team and not another. At level 3 a team would take a patch once enough organizations stand behind it, and the command would offer a verdict worked out from the lens. None of this is built. A lens file has none of these fields, and the command refuses a lens with level 3.

{
  "use": "run-with-access",
  "requires": "safe-to-run-with-access",
  "approved_destinations": [
    "api.fellbeck-notes.example"
  ],
  "patch_level": 3,
  "confirmations": 2
}

Run your own node

A team node is the one piece of Cairnfield you host. It is one Worker and one Artifacts namespace in your own Cloudflare account. It holds everything your team publishes, and the pinned original of each component you review. A setup script deploys it.

a team operator's machine
# The node's directory is self-contained. It needs Node 22.22.
$ git clone https://github.com/peoplerenaissance/cairnfield && cd cairnfield/node
$ nvm use && npm install
$ npx wrangler login
$ npm run setup
This deploys a team node to the Cloudflare account that Wrangler is logged in to.
It creates each of these that is missing, and updates each that is there:
the Worker cairnfield-node, with its Durable Object class ReadTokens
the Artifacts namespace cairnfield-node
the Workflow cairnfield-node-on-push
the trigger that starts that Workflow on each push to that namespace
It deletes nothing.
# … Wrangler deploys the node, twice when no address was given …
The node answers at https://cairnfield-node.YOUR-SUBDOMAIN.workers.dev
# The script never touches the admin key. Make one and give it to the node yourself:
$ openssl rand -hex 32
$ npx wrangler secret put ADMIN_KEY --env=""
# Name the node in cairnfield.json, then pin your first component:
$ cairnfield pin <git-url> --branch <branch> --commit <full-commit-hash>

What you need

  • A Cloudflare account on the Workers Paid plan, which Artifacts requires. Usage beyond the included amounts is billed to you.
  • An admin key that you choose. Your own command uses it to manage your node, and nobody else should have it.
  • The address of an index, only if you share through one. A node with none tells no index, and a team can work alone.
  • Your own model API key, only for a live run of the bundled patch agent.

What stays yours

  • Deploying gives us no access to your account, your repos or your key.
  • It does not register your node with the index. You do that with the command.
  • It does not install the cairnfield command or run any review.
  • It publishes nothing. A new node is empty until you push to it.

The one-click button is switched off. Cloudflare's documentation for the button does not list Artifacts, Workflows or push triggers among what it sets up, and a node needs all three. Nobody has tested the button on a node. Until a test shows that it sets up all three, the setup script above, npm run setup in node/, is the supported way to deploy one.
